# Database design

`tracked_repository` stores ID, canonical owner, name, full name, GitHub URL, active flag and creation/update timestamps. A case-insensitive unique index on full name prevents duplicates; a partial unique index allows at most one active row. `repository_selection_lock` contains one row and serializes concurrent activation transactions, including when no repository is active. There are no relationships between tracked repositories.

Flyway applies versioned SQL from `backend/src/main/resources/db/migration`; Hibernate validates the resulting schema and never updates it. GitHub issues, pull requests and metadata remain remote. `chat_session` belongs to a tracked repository; `chat_message`, `issue_proposal`, and `tool_execution_log` belong to a session. A proposal also records its repository and moves from `PENDING` to `REJECTED` or `EXECUTING`, then `SUCCEEDED` or `UNKNOWN`. An executing or uncertain proposal is never automatically retried. Tool logs store only tool name, success and time, not tool inputs or external content.

Each in-flight chat turn holds a PostgreSQL session-scoped advisory lock on a dedicated pooled connection. PostgreSQL releases it if the connection is lost; `busy` in the API is derived from live locks. Message and proposal inserts check the lock-owning backend PID and a monotonically increasing `turn_generation` while locking the session row. Once a newer turn claims the session, an older turn cannot save results. Each turn holds one pooled connection until its model call completes; a lost connection can still leave an old provider request running and incurring cost. Issue creation requires the separately claimed and approved proposal.
